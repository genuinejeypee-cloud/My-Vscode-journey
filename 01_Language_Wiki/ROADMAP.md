## 4. The Daily Execution Rules

1. **Zero Skipping:** Do not jump to Phase 2 until Phase 1 DOM mechanics are solid. Skipping steps creates weak foundations that crash later.
2. **No Copy-Pasting:** Type every command and line of code manually to build digital muscle memory.
3. **The Resistance Rule:** Stare at broken code and debug for at least 15–20 minutes using official documentation before asking for a direct answer. This is how problem-solving capability is built.

---

### 1. The "Mastery-Based" Progression Rule

In traditional schools, you move to the next chapter when the week is over, whether you understand the material or not. In this blueprint, **time is variable, but mastery is constant**. You do not move forward based on a schedule; you only move forward when you pass the "Mastery Check."

* **How to know when to move on:** You must be able to apply the knowledge to a new, slightly different problem without looking at the tutorial.
* **The Mastery Test:** If we learn how to make a button change text to "System Online," your test is to see if you can make a *second* button that changes the text to "System Offline" completely from memory. If you can do it, you have mastered the concept and can move to the next step. If you can't, we stay on that step and drill it until it clicks.

### 2. The "Chunking" Strategy (Mixing Theory and Practice)

The fastest way to learn software engineering is not to read a textbook for 4 hours. It is to mix theory with practice in small, bite-sized chunks.

* **Read a little, code a little:** You read about a concept (like the `querySelector` in JavaScript), and then you immediately switch to VS Code and try to make it work.
* **Embrace Frustration:** When the code breaks and the screen turns red, do not panic. Expect and embrace the frustration, because fighting through that obstacle is exactly where the real learning happens.

### 3. The 15-Minute "Struggle" Protocol

If you want to build the problem-solving skills of a real engineer, you must build up your tolerance for broken code. When you hit an error:

1. **Do not ask me for the answer immediately.**
2. Set a timer for 15 minutes.
3. Read the error message in the browser console.
4. Check your spelling in VS Code (90% of beginner errors are typos).
5. If you are still stuck after 15 minutes, *then* bring the code to me. You say: *"I tried to make the button work, I got this error, and I think the problem is on line 4, but I don't know how to fix it."*

### 4. Building Real Projects, Not Just Tutorials

The primary way to test your skills is to step away from trivial examples and build something you have never built before. You learn the most when you tackle hard, complex problems that don't have a step-by-step guide. That is exactly why we are turning standard assignments into custom projects like your Hydro-Power Monitoring System interface.

### The Fail-Safe: What if you forget?

You *will* forget things. Every senior developer on earth forgets how to write basic syntax and has to Google it.

* **The Fix:** You don't try to memorize code. You memorize *concepts*. If you know that an "Event Listener" is what makes a button clickable, but you forget the exact spelling, you can easily look it up in your `ROADMAP.md` or ask me for the syntax.
